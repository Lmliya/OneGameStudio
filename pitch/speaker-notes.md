# OneGameStudio 路演讲稿

预计时长：约 3 分 55 秒。每段对应演示稿中的一个场景。方括号内容为讲者操作提示，不朗读。

## 1. 开场 · 25 秒

[展示场景 1，指向右侧真实产品截图]

各位评委好，我们是 OneGameStudio。我们的想法很简单：用户只需要描述一个游戏创意，一整个 AI 游戏工作室就可以分工协作，最后交付一款可以试玩的游戏。我们把 AI 从一个聊天窗口，变成一间看得见分工、过程和产物的工作室。

## 2. 为什么需要它 · 30 秒

[切到场景 2]

单次生成代码只解决了开发链条中的一段。需求有没有被正确理解？生成的游戏有没有经过验证？修改之后还能不能追踪和恢复？如果这些职责都在同一轮对话里，很难给评委或团队留下可靠的工程证据。OneGameStudio 把需求分析、开发、审查、版本管理和持续迭代拆成清楚的步骤。这里不做没有依据的速度或质量数字对比。

## 3. 认识工作室 · 30 秒

[切到场景 3，点击 Engineer，再切换 Primary / Backup]

工作室由六个岗位组成：COO 负责需求分析；Creative Director 和 Delivery Director 分别提出创意与交付意见；Engineer 开发游戏；Reviewer 检查质量；Marketer 生成营销素材。Engineer 岗位配置 Primary 和 Backup 两个 Talent。点开岗位可以看它接收什么、产出什么。当前员工档案交互是这份路演页面中的本地演示。

## 4. 从一句话到可玩游戏 · 50 秒

[切到场景 4，点击“开始回放”]

接下来展示一条仓库里已有的任务记录。原始需求是做一个红色背景、有计分和重新开始按钮的贪吃蛇。请注意，这是一条已经保存的历史任务：模型供应商是 Mock，不是我们在台上实时调用模型。记录里 COO 写出需求，Engineer 生成 HTML，随后经过 Playwright 门禁和 Reviewer。第一次审查提出一个问题，工程师修复后再次审查通过。门禁有九项通过，还有“随机食物”一项未验证，我们把它如实留在页面上。右边可以试玩的游戏，就是这条任务留下的 HTML 产物。FAST 流程没有营销阶段，所以这条记录也没有 Marketer。

## 5. 版本与接管 · 35 秒

[切到场景 5，切换 v1 / v2，再播放接管预览]

项目的游戏版本以不可变快照保存，可以追踪父版本并切换预览。这里的 v1 是实际任务产物；v2 只是存档里的示例元数据，它附带的 HTML 与 v1 完全相同，因此不能把它说成一次真实的代码更新。项目已经支持 Primary / Backup 角色的人工切换，但失败后自动接管还没有连入执行流程。右边动画是规划中的机制示意，不是运行日志。两个工程底线是：历史版本不覆盖，失败恢复有明确边界。

## 6. Talent 进化与 SOP · 40 秒

[切到场景 6，播放进化示意；依次点 FAST、BALANCED、CREATIVE]

Talent 也可以积累经验并形成新版本，但候选不会直接生效：要经过固定回归评估，再由人批准；需要时可以回滚。当前实现的是确定性的 Mock 评估，真实模型评估尚未接入，随仓库快照也只有 v1。工作流则按任务选择：FAST 适合明确的小改动，仍保留门禁和审查；BALANCED 会引入创意与交付意见；CREATIVE 适合玩法探索和历史版本分支。图上的切换是路演演示，项目流程规则在后端实现。

## 7. 架构与收尾 · 25 秒

[切到场景 7，指出架构链与链接状态]

前端连接 FastAPI，再由工作流状态机和 Mini-6 Harness 管理 Agent 执行；Vessel 负责契约、预算和调用边界，Provider 可以选择 Mock 或配置好的模型接口。产物包括可玩的 HTML、门禁和审查报告以及版本记录。GitHub 仓库目前是私有的，线上 Demo 尚未部署，真实模型端到端也还没有验证。接下来的工作是完成真实模型验证和部署。OneGameStudio：一个创意，一整个 AI 工作室，一款可以玩的游戏。谢谢大家。
